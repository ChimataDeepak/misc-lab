# Resume bullets — misc-lab (Projects section)

**misc-lab — multi-currency receipt service (Java 21, Spring Boot, AWS via LocalStack, React)**

- Built a Spring Boot 3 receipt service that converts payments through an external FX API and writes each receipt to DynamoDB, S3 and a MongoDB audit log, then publishes a `ReceiptCreated` event to SQS consumed by a long-polling worker; verified end to end with a Testcontainers integration test running LocalStack (S3/SQS/DynamoDB), MongoDB and WireMock.
- Provisioned the AWS stack with Terraform on LocalStack (8 resources: S3 bucket, SQS queue, DynamoDB table, IAM role, Lambda, permission and S3→Lambda notification) and wrote a Java Lambda triggered by S3 uploads that logged `processed 1 object(s), 164 bytes` in 502 ms.
- Hardened the FX dependency with Resilience4j retry, circuit breaker and HTTP read/connect timeouts plus a fallback rate; tests prove retry count, timeout fallback and short-circuiting, and a live test with the FX mock stopped showed the breaker going `OPEN` and receipts still issuing at the fallback rate (11.90 USD instead of 12.00 USD).
- Added a batch-conversion endpoint that fans out FX lookups with `CompletableFuture` on a virtual-thread-per-task executor, with a latch-based unit test that deadlocks unless all 20 conversions really run concurrently.
- Instrumented the service with Micrometer/Prometheus (custom counters and an `fx_call` latency histogram), ECS JSON structured logs, and multi-window SLO burn-rate alerts (99.5% availability, 14.4x/6x burn) — 3 alerts and 4 recording rules loaded in Prometheus; load-tested with JMeter (20 users × 10 loops: 200 requests, 0 HTTP errors, ~18 req/s, p95 1074 ms) and documented the missed 1 s latency target and its sequential-write root cause.
- Built a React + TypeScript (Vite) front end with a custom `useReceipts` hook covered by 4 Vitest/Testing Library tests, and a Selenium Page Object UI test that creates a receipt in Chromium running in Testcontainers; wrote a GitHub Actions workflow for backend, frontend, Terraform validate and promtool checks.
- Added a standalone Angular 19 component that looks up a receipt by id against the same Spring Boot REST API (`frontend-angular/`; Vitest on the HTTP client). Lab-level Angular only — not a routed enterprise app.
- Archived receipt JSON to Azure Blob Storage with the Azure SDK against Azurite (local emulator). Not AKS, App Service, or a paid Azure account.
- Exposed the same receipt lookup as GraphQL (`receipt(id)` on `/graphql`, money as strings) and as a protobuf `GetReceipt` gRPC service; both are adapters over `ReceiptService`, covered by slice/unit tests. A tiny Angular standalone component calls the REST GET for Citi/Broadridge-style UI titles (not a full Angular app).

- Built a payment lifecycle for receipts: a PaymentIntent state machine (created, authorized, captured, partial and full refund, void) with every one of the 36 state pairs tested, integer minor-unit money, `Idempotency-Key` handling on create/capture/refund (retries return the stored result; key reuse with a different body returns 422; 50 concurrent retries produce one payment), and HMAC-SHA256-signed webhooks with timestamp-window and event-id replay protection. Built and tested locally: 28 unit tests plus an end-to-end REST test in which a mock merchant verifies all 4 webhooks.
- Moved the payment service from memory to PostgreSQL 16 (Spring Data JPA, Flyway migrations): state transitions take a row lock (`SELECT ... FOR UPDATE`) with `@Version` as a second guard, the Idempotency-Key is a table primary key claimed with `INSERT ... ON CONFLICT DO NOTHING` in the same transaction as the change, webhook events go to an outbox table in that transaction and are delivered after commit, and received event ids are stored for replay checks. Tested on Testcontainers Postgres: 50 concurrent same-key creates give 1 row and 1 event; 20 concurrent refunds on one payment never over-refund (exactly 10 of 20 succeed).
- Parallelised a receipt's DynamoDB, S3 and MongoDB writes with `CompletableFuture` on a shared virtual-thread executor, publishing the SQS event only after all writes succeed and returning 503 naming every failed store; documented that it is not atomic. Re-ran the JMeter test (5 runs per version) and found no reliable p95 gain: a single request takes ~35 ms, so the original "sequential writes" diagnosis was wrong, and the remaining stalls were traced outside the app (server-side timer max 3.3 s while JMeter reported 69 s).
- Wrote a Go CLI that verifies those webhook signatures, pinned to the same test vector as the Java signer so the two implementations can't drift (Go tests run in the official Go container).
- Built `receipt-insights`, a Python FastAPI service and CLI that reads receipts from the Spring Boot API and reports totals by currency and top payers using `Decimal` end to end; 7 pytest tests with a mocked HTTP transport, a Dockerfile, and a live run against the Java service.
- Added a GCP path behind a Spring profile: receipts archived to Cloud Storage and `ReceiptCreated` published to Pub/Sub with the official Google Cloud Java clients, verified by a Testcontainers integration test against the Pub/Sub emulator and fake-gcs-server (emulators, not a live GCP project).
- Tested the receipt search client against real Elasticsearch 8 in Testcontainers, which exposed two bugs a mock-only test had hidden: search-after-index returned nothing (fixed with `refresh=wait_for`) and the query JSON was built by string concatenation (now built with Jackson).
- Added an OAuth2 resource-server chain that validates JWT issuer and audience on `/api/oidc/**` (tested with signed tokens; HMAC key rather than a JWKS identity provider), and a local Spark (`local[1]`) job counting payers, tested locally.
- Added a component test for the Angular lookup (TestBed, JIT, zoneless) that exposed a dependency-injection bug (NG0202) in the component; fixed with `inject()`.

## Interview talking points (from the 10 fixes in RUN-RESULTS.md)

- **Container runtime plumbing:** Testcontainers couldn't find Rancher Desktop's Docker socket, and docker-java's default API 1.32 was rejected by Docker 29 (min 1.41) — fixed with `DOCKER_HOST`/socket override and `api.version=1.44`.
- **Metrics gotchas:** `/actuator/prometheus` was 404 in `@SpringBootTest` until `@AutoConfigureObservability`; a counter named `receipts_created` silently became `receipts_total` because OpenMetrics reserves the `_created` suffix — renamed to `receipts_issued`.
- **Container-to-host networking:** `host-gateway` pointed at the Rancher VM, not the Mac, so Prometheus/JMeter used `host.docker.internal`; in Selenium, `exposeHostPorts` in `@BeforeAll` ran after `@Container` startup (`ERR_NAME_NOT_RESOLVED`) — moved to a static initializer.
- **Emulator state is ephemeral:** a LocalStack restart wiped resources, so Terraform apply is re-run from fresh state.
- **Apple silicon images:** `standalone-chrome` is amd64-only; switched to multi-arch `selenium/standalone-chromium`.
- **Browser security in tests:** Vite's DNS-rebinding protection blocked `host.testcontainers.internal` (fixed via `allowedHosts`), and a forwarded `Origin` header caused CORS 403s — the dev proxy strips `Origin` since proxied calls are same-origin.
- **Honest perf finding:** I blamed the ~1.07 s p95 on sequential S3/DynamoDB/Mongo writes, parallelised them, and re-measured: no reliable gain. One request takes ~35 ms, so p95 was queueing under load, and the worst stalls were outside the app (app timer max 3.3 s vs JMeter 69 s). Lesson: measure the per-request breakdown before optimising.
- **Concurrency on a real DB:** a unique key plus `ON CONFLICT DO NOTHING` makes a concurrent duplicate wait for the first transaction and then read its stored result; a row lock serialises transitions on one payment.
- **Mocks can hide real behaviour:** the Elasticsearch client passed its WireMock test but returned nothing against real ES (near-real-time refresh). An integration test against the real engine caught it.
- **Flaky test root cause:** Testcontainers reported LocalStack as ready before Rancher Desktop forwarded its port to the host, so ~1 in 3 runs failed with `Connection refused`. The fix polls the health endpoint from the host side instead of adding retries or sleeps.
- **Idempotency and exactly-once:** the network can't give exactly-once delivery. Idempotency keys make retries safe on the request side, and event-id dedupe makes webhooks safe on the receiver side.
